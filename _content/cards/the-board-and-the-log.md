**What it is.** Thirty minutes in the LLUF studio block: the fellows' version of the game-state thread that runs through the week, with [Every tap is a row](every-tap-is-a-row.md) and [Photo to game state](photo-to-game-state.md) side by side.

**How it runs.** Start with the tap prototype's keys or clicks; NFC is optional until someone checks the exact reader and tags on this laptop. One fellow plays a short round while another mirrors each successful claim with paper tokens, and failed actions go on a separate list. Freeze the board and photograph only the board and tokens, then write the state the photo shows as a small table, marking unknowns rather than guessing. Read the prototype's log and replay control, and rebuild an earlier point with tokens; if a control fails, copy five rows by hand and report it. Which attempts are in the log but left the board unchanged? Last, set the photo, the state table and five log rows side by side and write the station label: which record answers "where are things?" and which answers "what happened?"

**What it does for learning.** The current board is a state; an event history can rebuild states only if its starting conditions and rules are known. A photograph misses hidden cards, turn order and everything between frames, and two photos can't recover the moves between them, since many sequences lead to the same difference. LU bridges this through Manovich's data-and-algorithm discussion, as the repo summarizes it. The fellows end up holding the vocabulary Marlon's class uses on Wednesday.
